# EF-1: what the facts layer costs to run, and an incremental gate whose update cost barely grows with memory

**Status:** descriptive and engineering, 21 October 2026. No hypothesis, no preregistration. Model-free.
**Code:**
- `memgate/fast.py`: `FastFreeGate` and `FastLightGate`;
- `cl/ef1_equiv.py`: the equivalence check;
- `cl/ef1_bench.py`: the benchmarks.

**Records:** `runs/ef1-20261021/`:
- `equivalence.txt`;
- `batch.jsonl` and `steady.jsonl`;
- `ft-jobs.json`, the training jobs of the finished fine-tuning worlds, read from Azure.

**Machine:** one CPU core of the lab's Azure VM, Python 3.12, standard library only.

## 1. An incremental gate with identical decisions
**The cost of the original gates.** `FreeGate` and `LightGate` recompute memory from every claim they have ever heard, at every step. A step therefore costs time in proportion to everything memory has heard.

**What the incremental gates do.** `FastFreeGate` and `FastLightGate` keep each fact's share of the counts that decide which sources form one voice. At each step they re-examine only the facts whose inputs changed:
- a new claim;
- a change in memory's value;
- a claim reaching the two-step wait;
- a source joining, leaving or merging.

**Equivalence check.** Both pairs were run side by side, and memory and its change history were compared after every step, on 16 streams. Every stream gave identical results.

| Streams | Gates | Count |
| --- | --- | --- |
| Lab worlds with no registry (dev seeds 8490–8492, RF-1's main seeds 8700–8702), with a deletion request at step 6 | `FreeGate` / `FastFreeGate` | 6 |
| The same worlds with a 5% registry share, with audits and dismissals | `LightGate` / `FastLightGate` | 6 |
| Synthetic streams, dense and sparse, 2,000 and 5,000 facts, with a deletion request | `FreeGate` / `FastFreeGate` | 4 |

## 2. Small updates to a large memory (the live case)
**Setup.** Memory was first built from a 12-session stream. Then came 20 updates of 1,000 reports each: honest sources naming current values, with 2% new values that three sources confirm.

| Facts in memory | Claims held | `FreeGate`, ms per update (median) | `FastFreeGate`, ms per update (median) | Peak memory |
| --- | --- | --- | --- | --- |
| 10,000 | 51,872 | 134.6 | 29.8 | 107 MB |
| 100,000 | 504,648 | 2,304.5 | 35.3 | 806 MB |
| 300,000 | 1,510,402 | (not run) | 40.4 | 2,359 MB |

- **The original gate's cost grows with memory.** The incremental gate's barely grows: 30 ms at 10,000 facts, 40 ms at 300,000.
- **The slowest updates are the first two after the 12-session build.** They re-examine that build's claims as they reach the two-step wait (up to 0.76 s at 100,000 facts, 2.3 s at 300,000).

## 3. Whole sessions (batch)
**Setup.** These are synthetic streams shaped like TM-1's worlds: twelve sessions, five honest sources, colluders, a stealthy source and sybil swarms.
- **Dense:** each honest source reports 25% of the facts each session, so about three in four facts get a report.
- **Sparse:** 2% per source.

| Stream | Facts | Reports | `FreeGate`, s per session (median) | `FastFreeGate`, s per session (median) | Peak memory (fast) |
| --- | --- | --- | --- | --- | --- |
| dense | 10,000 | 156,714 | 0.133 | 0.138 | 103 MB |
| dense | 100,000 | 1,559,459 | 2.387 | 2.238 | 824 MB |
| sparse | 100,000 | 179,409 | 0.388 | 0.170 | 197 MB |
| sparse | 300,000 | 534,965 | 1.254 | 0.723 | 540 MB |
| sparse | 1,000,000 | 1,782,106 | (not run) | 2.603 | 1,715 MB |

- **When most facts change every session, there is little to save.** Both gates take in about 57,000–110,000 reports a second.
- **No attacker value got in:** on every synthetic stream, memory held no attacker's value at any point.

- **Deployment comes on top**, before a trained model answers.

## What it shows
- **The memory route takes in a verified change in tens of milliseconds**, and it is in use at the next question. The weights route takes hours per block, before deployment.
- **With the incremental gate, an update's cost depends on what it touches, not on how much memory holds.** With 300,000 facts in memory, an update of 1,000 reports took 40 ms on one core.

## Limits
- **The streams are synthetic.** The update mix (2% new values) and the report shares are chosen, not measured.
- **Pure Python.** About 7–8 KB of working memory per fact in the dense case. A compact store would use far less; that is not done here.
- **Not measured:** the token cost of memory lines in prompts.
- **The fine-tuning times** include queueing on shared capacity and vary by region and time.
