# SR-2: śāstra lesson policies, revised after SR-1

**Status:** design, written on 17 October 2026 before any SR-2 code was run. The branch and folder are the same as SR-1. SR-2 makes no model calls.

## 1. Why SR-2

SR-1 found no advantage for the śāstra policies over ordinary rule learning on real data: −0.05 pp [−0.31, +0.20], a NO WIN ([result](SR1-RESULT-2026-10-17.md)). Its pilot and main run point to three specific failure modes:

1. **General lessons are never retired.** A general lesson stays valid however many exceptions are carved out of it. This cost R-SHASTRA 3.9 pp under drift and 1.2 pp on random DNF concepts.
2. **Upādhi is accepted on thin evidence.** A single upādhi is accepted on three to five supports. In the exception world (EXC), lessons narrowed this way were right only 78% of the time.
3. **One-support exceptions decide cases.** Under noise and on DNF they were right 39–52% of the time.

SR-2 adds one śāstra-grounded remedy for each and tests the revised policy on data SR-1 never touched.

## 2. Amendments

All three amendments are parameter-free or derived from SR-1's frozen parameters.

### B: balīyastva (the utsarga must be the general case)

A general lesson stays valid only while its confirmations are at least as many as the counterexamples its exceptions explain. When the explained counterexamples outnumber the confirmations, the lesson is discarded as *savyabhicāra*, and its exception lessons remain.

An utsarga is, by definition, the rule of the general case. A pervasion that fails more often than it holds is deviating, not general.

### N: niścita upādhi (repeated observation first)

An upādhi, whether single or a saṃśaya group, is accepted only when the lesson has at least 2 × 3 = 6 supports. With fewer supports, the counterexample takes the apavāda path and an exception is carved out.

A condition read off three to five observations is only suspected (*śaṅkita*). Nyāya requires repeated observation (*bhūyodarśana*) before a condition counts as ascertained (*niścita*).

### V: an unestablished exception bars but does not decide

An exception lesson that is still a candidate (fewer than 3 supports) bars the more general lesson within its own domain, but it cannot decide the case itself. If nothing else decides, the fallback does. Once validated, the exception decides as in SR-1.

*Yena nāprāpte…* places the exception's domain outside the general rule. Asserting the exception's own conclusion still needs an established ground.

## 5. Hypotheses and decision rules

The rules are the same as in SR-1. Δ is the dataset-averaged paired accuracy difference over 10 orders, with a stratified bootstrap (10,000 resamples, seed 12345) and a 1 pp margin.

**H1 (primary): R-SHASTRA2 − R-ORD on the six held-out datasets.**

| Verdict | Condition |
| --- | --- |
| WIN | Δ ≥ +1.0 pp and the CI lower bound > 0 |
| NO WIN | CI upper bound < +1.0 pp |
| UNDETERMINED | anything else |
| INVALID | see below |

INVALID applies if any run fails, any run is non-deterministic, B, N or V never execute on held-out data, or an SR-1 arm fails the regression check.

**H2: R-SHASTRA2 − R-SHASTRA on the held-out datasets.** Same rules. This asks whether the revision helps the śāstra policy itself.

**H3 (descriptive):** R-SHASTRA2 against EXT-DT, EXT-NB and EXT-1NN, and the three ablations.

**Synthetic results on the new seeds are diagnostic.** They are reported per family with bootstrap CIs over 20 seeds.

## 7. Fixed before any SR-2 run

**SR-1 parameters, unchanged:** support threshold 3, at most 3 literals per formation, strength ratio 2, the same DT schedule, Naive Bayes α = 1, T = 400 synthetic cases and at most 1,000 real cases.

**New thresholds (derived, not tuned):**

- **B:** retire when explained counterexamples outnumber supports.
- **N:** upādhi needs at least 6 supports.
- **V:** has no parameter.

**Process:**

1. Write the code and tests, and run the SR-1 regression.
2. Develop on exposed data only. Bug fixes are logged; nothing is tuned.
3. Freeze the preregistration with the code hash and the hashes of the new data.
4. Run the main study once.
