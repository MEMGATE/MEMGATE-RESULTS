# RC-1 preregistration: does memory find stale values sooner when it re-checks the least likely ones first?

**Status:** frozen 21 October 2026, before the main half was run. Spec and preregistration in one document.
**Dev run:** `runs/rc1-dev-20261021/summary.json` (TM-1's dev half of the offices: 4,830 offices, 20 worlds).
**Earlier exploration:** `cl/ar1_explore.py` (as AR-1, renamed because AR-1 already names an 18 October experiment). On TM-1's worlds the order of re-checks hardly mattered, because sources reported most changes a session later. This design makes sources sparse.

Code SHA-256: `1636d029e3a106153f1ee6ff244ea7176d330f5af1cbae444d44e67c60d42e9b`

The hash covers `cl/rc1.py`, `cl/rc1_explore.py`, FR-2's code (`cl/fr2.py`, `cl/fr2_explore.py`), `memgate/fresh.py`, the world helpers it uses and the Wikidata files.

## 1. Question
The property tested: memory knows what may be stale and checks that first.
- **The estimate:** FR-2 gave a calibrated chance that a stored office holder still holds.
- **The question:** with a fixed number of checks per month, does checking the least likely values first leave fewer stale values than checking the oldest checks first, or checking at random?

## 2. Design
**Offices.** Every office in the Wikidata snapshot with a single holder on 1 January 2020. They are split into TM-1's halves and cut into 20 worlds of about 240 offices each, by a fixed hash.
- Main uses the main half, 4,746 offices.
- Most are heads of government. The rest are head coaches, chairpersons, chief executives, heads of state and directors.

**Time.**
- On 1 January 2020 memory holds each office's holder that day, with the start date the record gives.
- Then come 47 monthly sessions, to 1 December 2023.
- The test stops before 2024, because the snapshot chose its offices by what happened after March 2024.

**Each session:**
1. **Reports.** Once an office's holder has changed, a source reports it with chance R per session. Memory checks each reported office first. The draw is fixed per office and session, so it is the same under every policy.
2. **Checks.** The rest of the month's checks, B% of the world's offices, go to stored values in this order:
   - **NONE:** no further checks;
   - **RANDOM:** at random;
   - **AGE:** the value checked longest ago first;
   - **KIND:** the lowest chance of still holding first, from the kind of post only;
   - **FR2:** the lowest chance of still holding first, from `memgate.fresh.Freshness`, using the kind of post, the holder's tenure at the last check and the time since that check;
   - **ORACLE:** the offices that really changed first, a bound no memory can reach.
3. **What a check does:** it stores the holder on that day, with the holder's start date.

**Fitting.** Freshness is fitted only on checks from 2012 to 2019 whose look-again day falls before 2020: 135,679 checks over all offices. Nothing from the test window is used.

**Measure.** The stale share is the share of offices whose stored holder is not the holder that day. It is averaged over the 47 sessions, per world. Office-days with no single holder on record are left out.

**Grid:**
- R = 0 (no sources), 0.1 (sparse) and 0.3;
- B = 1%, 2%, 5% and 10% per month;
- AGE also at every whole budget from 1% to 20% with R = 0.1, for the checks-saved description.

## 3. Hypotheses
Each test takes the difference in stale share per world. The estimate is the mean over the 20 worlds, with a 95% t interval (19 degrees of freedom, t = 2.093).

| Test | Comparison | Rule |
| --- | --- | --- |
| **H1 (primary)** | FR2 − AGE, R = 0.1, B = 2% | **WIN** if the interval lies wholly below −0.2 pp; LOSS if wholly above +0.2 pp; otherwise no difference shown |
| H2 | FR2 − AGE, R = 0, B = 2% | same rule |
| H3 | FR2 − RANDOM, R = 0.1, B = 2% | same rule |

**Descriptive** (no claim):
- every cell of the grid;
- KIND against FR2;
- the ORACLE bound;
- **checks saved:** the AGE budget, interpolated on the mean over worlds, that leaves the stale share FR2 leaves at each budget with R = 0.1.

## 4. Predictions (dev)

| Test | Estimate, pp [95% interval] | Worlds below 0 | Dev verdict |
| --- | --- | --- | --- |
| H1 | −0.69 [−0.84, −0.54] | 20 of 20 | WIN |
| H2 | −1.08 [−1.39, −0.76] | 19 of 20 | WIN |
| H3 | −0.65 [−0.84, −0.47] | 18 of 20 | WIN |

**Stale share at R = 0.1:**

| Budget | NONE | RANDOM | AGE | KIND | FR2 | ORACLE |
| --- | --- | --- | --- | --- | --- | --- |
| 1% | 4.40% | 4.26% | 4.24% | 3.67% | 3.67% | 0.35% |
| 2% | 4.02% | 3.62% | 3.66% | 2.87% | 2.96% | 0.02% |
| 5% | 4.01% | 3.00% | 2.73% | 2.26% | 2.24% | 0.00% |
| 10% | 4.01% | 2.32% | 1.88% | 1.35% | 1.35% | 0.00% |

**Checks saved (dev).** AGE needed about 2.0%, 4.1%, 7.9% and 14.7% of offices per month to match FR2 at 1%, 2%, 5% and 10%. That is 32–51% fewer checks for the same stale share.

**What dev showed:** the kind of post carries almost all of the gain. KIND did as well as FR2.

## 5. Limits
- **Scope:** office holders only, from one snapshot.
- **The checks are simulated:** a check returns the record's holder that day. Report arrival is simulated too.
- **The offices are the snapshot's,** whose selection depends on events after March 2024. The test window ends before 2024.
- **The gain comes from the kind of post.** The tenure bands add little.
