# ML-1: model-written lessons managed by śāstra rules

**Status:** design, written on 17 October 2026 before any ML-1 model call. The branch and folder are the same as SR-1 and SR-2. ML-1 uses the user's Azure model deployments, with keys taken only from environment variables at run time.

## 1. Question

SR-1 and SR-2 found that śāstra policies do not beat ordinary rule learning on clean symbolic data. Their one consistent advantage was tolerance of noisy evidence. Lessons written by a language model are noisy evidence: a model can state a rule that past experience already contradicts (*viparyaya*, YS 1.8), or a rule about things that were never observed (*vikalpa*, YS 1.9).

**ML-1 asks:** when a model learns from a stream of experiences by writing lessons, does managing those lessons with śāstra rules improve its accuracy on new cases?

## 2. Task

- **Worlds.** Three SR synthetic families: EXC, NOISE and DNF.
  - Features are named `f0`–`f11`, values are `v0`–`v3`, and labels are `L0`–`L2` (`L0`–`L1` for DNF).
  - The names carry no meaning, so the model can have no prior knowledge of any world. Labels are learnable only from experience.
- **Stream.** The first 100 cases of each world.
- **Models.** `gpt-6-astra` and `claude-opus-5-5`.
  - Claude runs with `output_config.effort = "medium"` set explicitly (its documented default).
  - Astra runs with its deployment defaults; the deployment rejects non-default temperature.
  - Grok is excluded because one call took 132 s.

## 3. One time step

Every arm runs the following loop at each case `t`.

1. **Predict.** Each arm builds one prompt containing:
   - the possible labels;
   - up to 6 lessons from its own store;
   - the 8 most similar past cases, which are identical for every arm (Hamming distance, ties to the most recent);
   - case `t` without its label.

   The model answers with a label. The first `L<digit>` token in the reply counts as the answer; a reply with none is counted wrong. Arms whose prompts are byte-identical at the same step share one call, so they get the same answer.
2. **Reveal.** The label of case `t` is revealed.
3. **Propose.** One lesson proposal per step is shared by all lesson arms.
   - The same model sees case `t` with its label, plus the same 8 similar past cases.
   - It writes one rule, `IF f<i>=v<j> [AND …] THEN L<k>`.
   - Only text that matches this format exactly is parseable.
4. **Update.** Each lesson arm first offers the proposal to its own store, then records case `t` as evidence for or against its stored lessons.

Because the proposal stream is shared, lesson arms differ only in how they manage the same lesson texts.

## 4. Arms

### EXP: no lessons

Experience retrieval only. This is the "storage plus retrieval" control.

### ORD: ordinary lesson memory

- **Storage.** Every parseable, non-duplicate proposal is stored. This is the common practice of keeping model-written reflections unvalidated.
- **Invalidation.** A stored lesson is dropped at its first counterexample after storage.
- **Display.** Matched lessons, whose conditions all hold for the case, are shown most recent first, up to 6.

### VRTTI: Yoga vṛtti admission

Only proposals classified as *pramāṇa* are stored:

- **Vikalpa → rejected.** The rule names a feature outside `f0`–`f11`, a value never observed for that feature, or a label outside the world's label set.
- **Viparyaya → rejected.** A past case satisfies the conditions but has a different label.
- **No support → rejected.** No past case, including `t`, satisfies the conditions with the stated label.
- **Smṛti → merged.** An exact duplicate of a stored lesson is merged into it.
- **Pramāṇa → stored.** Everything that passes the checks above.

After storage, invalidation and display are the same as ORD. Computationally, the admission check is consistency validation against stored experience. The śāstra contributes the taxonomy; ML-1 tests whether the validation matters for model-written lessons.

### SHASTRA: VRTTI admission plus the SR-1 rules

- **Apavāda precedence.** A counterexample covered by a stored, more specific lesson that has the counterexample's label counts as explained, and the general lesson stays. At display time, a general lesson is hidden for a case whenever a more specific matched lesson gives a different label.
- **Satpratipakṣa.** If matched lessons still disagree and none is more specific than another, the conflicting lessons are withheld, and the model relies on the past cases alone.

## 5. Metrics and decision rules

### Metrics

- **Primary:** prequential accuracy over cases `t` = 1…99. Case 0 has no experience behind it.
- **Secondary:**
  - Accuracy on cases where lessons were shown.
  - Lessons proposed, unparseable, vikalpa, viparyaya, stored, dropped and explained.
  - Lessons shown per case.
  - Invalid answers and refusals.
  - Tokens, latency and retries for every call.

### Analysis

- There are six strata (2 models × 3 families), and the units are worlds (seeds).
- Δ is the mean over strata of the per-stratum mean paired difference.
- The CI comes from a stratified bootstrap (10,000 resamples, seed 12345).
- A verdict follows the SR rules:

| Verdict | Condition |
| --- | --- |
| WIN | Δ ≥ +1.0 pp and the CI lower bound > 0 |
| NO WIN | CI upper bound < +1.0 pp |
| UNDETERMINED | anything else |

### Hypotheses

| Hypothesis | Comparison |
| --- | --- |
| **H1 (primary)** | VRTTI − ORD: does the vṛtti admission filter help? |
| **H2** | SHASTRA − ORD |
| **H3** | ORD − EXP and VRTTI − EXP: do model-written lessons add anything beyond retrieved experience? |

### INVALID conditions

- More than 5% of calls in the run fail after retries.
- The VRTTI arm never rejects a proposal. This invalidates H1.
- The SHASTRA arm never explains a counterexample or hides a lesson. This invalidates H2.
- The structural leakage check fails: a prediction is built before memory holds exactly the earlier cases.

## 6. Seeds, sizes and budget

### Seeds

- **Dev:** world seeds 0–1, which SR runs already exposed. They are used for a smoke test and a pilot, never for verdicts.
- **Main:** world seeds 5000–5005 per family, never used before.

### Main run

- 3 families × 6 seeds × 2 models = 36 worlds.
- Each world takes 100 steps × (up to 4 predictions + 1 proposal), so the run makes at most 18,000 calls.
- Calls are retried up to 4 times on HTTP 429, 5xx or network errors, with exponential backoff. A call that still fails counts as a wrong answer, or as no proposal.

### Budget

- The run aborts after 25,000 calls.
- Every call's tokens are recorded.
- The master brief authorises the API budget, and the user asked to continue with these keys.

## 7. Predictions before any model call

| Hypothesis | Expected direction | Expected verdict |
| --- | --- | --- |
| H1 | VRTTI > ORD | UNDETERMINED or a small WIN |
| H2 | SHASTRA ≈ VRTTI; better on NOISE and EXC, worse on DNF | UNDETERMINED |
| H3 | Lessons add little over 8 retrieved cases | NO WIN or UNDETERMINED |

The reasoning behind each row:

- **H1:** unvalidated model rules that contradict past cases should mislead the model.
- **H2:** this follows the pattern of the SR results.
- **H3:** the nearest cases already carry most of the information.

## 8. Limits

- These are anonymised symbolic worlds, not natural-language tasks.
- Two models, three families, and six worlds per stratum.
- One proposal and up to four predictions per step.
- No integration with Pramana's M-CORE, and no weight training.
